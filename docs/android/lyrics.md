# Android 端高精度歌词解析规范 (docs/android/lyrics.md)

为了保证 2FMusic-Android 客户端在播放不同格式（LRC、YRC）及不同来源的歌词文件时均具有最高精度的展示效果，歌词解析模块 `LrcParser` 必须严格遵循以下技术规范：

## 1. 垃圾/非标准元数据丢弃
*   **判断标准**：一行文本在前后去除空白后，若以 `{` 开头且以 `}` 结尾，判定为非标准 JSON 元数据行（如网易云演职员元数据）。
*   **处理红线**：为此类行进行静默 `continue` 丢弃处理，不应将其计入展示歌词中，也无需进入后续复杂的正则表达式匹配流程，以此保障内存及解析效率。

## 2. YRC 逐字时间精度自适应
*   **问题背景**：不同平台导出的 YRC/KRC 文件中，括号内字的起止时间既有采用**绝对时间戳**的，也有采用**相对本行起止的偏移量**的。
*   **计算公式**：
    $$\text{absoluteStart} = \begin{cases} 
      \text{time} + \text{wStart} & \text{若 } \text{wStart} < \text{time} \\ 
      \text{wStart} & \text{若 } \text{wStart} \ge \text{time} 
   \end{cases}$$
    *   `time` 为该行的起始绝对毫秒时间戳。
    *   `wStart` 为从字标签括号中提取出来的第一个数字。
*   **解析红线**：统一将字级时间以 **绝对毫秒时间戳** 转换并存储在 `YrcWord` 中，为 UI 的 `drawWithContent` 渲染提供最精准的绝对时间对照基准。

## 3. LRC 毫秒弹性长度对齐
*   **问题背景**：普通的 LRC 歌词中，毫秒的长度并不固定（例如 `[00:01.8]` 为 1 位，`[00:01.17]` 为 2 位，`[00:01.170]` 为 3 位，甚至还有 4 位以上的更高精度）。直接按长度做 pattern matching 容易导致不标准的毫秒值直接被清零。
*   **对准算法**：
    对于提取到的毫秒字符串 `msStr`：
    ```kotlin
    val ms = msStr.padEnd(3, '0').substring(0, 3).toLongOrNull() ?: 0L
    ```
*   **解析红线**：必须通过智能补齐与截断使毫秒值统一为 3 位并正确折算。禁止由于长度不合规而将毫秒值清零。
