# 后端业务服务逻辑契约 (docs/server/services.md)

## 1. 物理库扫描与文件监听服务 (Watchdog & Scanner)

### 1.1 自动防抖防冲突监听机制 (Watchdog Worker)
*   **物理捕获**：使用 `watchdog` 库捕获挂载目录下的 `created`、`deleted`、`moved` 物理变动。
*   **延时防抖队列 (Debounce Worker)**：
    - 所有监听文件变动均写入线程安全队列 `watchdog_queue`。
    - **逻辑行为**：消费线程拉取到变动信号后，默认先向后延迟 **2.0 秒** 执行。
    - **自适应延迟**：若 2 秒延迟期满，比对发现文件大小正在变化（如大文件正在物理写入中），则将任务再次往后延迟 **1.0 秒**。只有当物理文件大小完全稳定不变时，才调起物理索引同步。这有效避免了在用户上传歌曲中触发部分写入导致提取报错的 Bug。
*   **监听路径计算**：由默认曲库路径 `MUSIC_LIBRARY_PATH` 加上 `mount_points` 表中挂载的所有路径组成，并自动排除嵌套的子目录路径。

### 1.2 并发控制与防重叠扫描锁机制 (Scan Locks)
为了避免用户手动触发扫描、文件夹挂载变动自动触发扫描以及 Watchdog 监听事件并发执行导致数据库竞争与 CPU 暴涨，必须实现以下双重锁机制：
*   **内存排他锁 (`scan_execution_lock`)**：使用全局线程互斥锁限制同时只能运行一个扫描任务。若尝试获取锁失败，应直接跳过本次全量增量扫描。
*   **物理文件锁 (`.scan_lock`)**：在默认音乐曲库路径下写入临时 `.scan_lock` 文件，其中记录当前扫描的启动时间戳。
    - **防死锁自愈机制**：如果检测到 `.scan_lock` 文件存在，且其最后修改时间已经超过 **300 秒 (5分钟)**，说明前一次扫描可能因进程意外崩溃或系统强杀而残留。此时应物理删除该过期锁文件，重置锁状态，并允许新扫描任务启动。

### 1.3 单文件物理入库逻辑 (index_single_file)
*   **防重哈希**：优先从库中提取 `path`, `size`, `mtime` 皆未发生改变的记录，直接继承原 `id`；为新文件时，采用文件内容 MD5 作为歌曲的全局唯一 ID。
*   **物理缓存位置**：
    - 封面：`app_config.COVERS_DIR/{song_id}.webp` (自动转换 WebP 格式)
    - 歌词：`app_config.LYRICS_DIR/{song_id}.lrc` (标准 LRC 文本) 与 `app_config.LYRICS_DIR/{song_id}.yrc` (网易云逐字歌词文本)
*   **封面提取优先级**：外部物理同级同名 `.jpg`/`.jpeg`/`.png` $\rightarrow$ 缓存目录已有 $\rightarrow$ 原生音频内嵌 `extract_embedded_cover`。
*   **歌词提取优先级**：
    - **默认模式 (未指定 yrc 优先)**：外部物理同级同名 `.lrc` $\rightarrow$ 缓存目录已有 `.lrc` $\rightarrow$ 原生音频内嵌 `extract_embedded_lyrics` $\rightarrow$ 网络多源刮削。
    - **逐字优先模式 (前端指定 yrc 参数)**：外部物理同级同名 `.yrc` $\rightarrow$ 缓存目录已有 `.yrc` $\rightarrow$ 默认模式下的 `.lrc` 检索与刮削链条。
*   **Web 上传极速入库规范**：对于通过 Web 接口上传 of 音乐文件，采用“0 延迟、即传即播”的主动忽略并异步索引模式。上传前利用 `add_watchdog_ignore_path` 主动在 Watchdog 机制中忽略该目标路径。上传物理保存并重命名（`shutil.move`）完成后，Web 接口服务线程立即向客户端响应 HTTP 200 确认上传成功，并将后续的单文件索引（`index_single_file`）以及元数据自动刮削任务（`auto_scrape_missing_metadata`）一并推入后台异步线程中执行。这能大幅缩短 Web 上传的接口等待时长，避免重复的 Watchdog 防抖索引，实现真正意义上的即传即播。

### 1.4 后台自动刮削与多源检索规范 (auto_scrape_missing_metadata)
*   **触发条件**：增量扫描完成后，若库中仍存在 `has_cover=0` 或 `has_lyrics=0` 的歌曲，且重试次数满足限制，则后台启动该刮削任务。
*   **自动刮削偏好遵循卡口规范**：
    - 在物理增量扫描入库（`index_single_file` 等）时，系统读取偏好设置 `lyrics_source_preference`。
    - 如果偏好是 `network`（优先网络），且本地没有外部同级同名 `.lrc` 文件，也没有歌词缓存，则**严禁直接提取音频内嵌歌词写入缓存**，应保持 `has_lyrics=0` 状态以允许该曲目正确流入后台自动刮削流程去检索更优质的网络歌词。
    - 如果偏好是 `embedded`（优先内嵌），保持原有逻辑，扫描时直接提取内嵌歌词并标记已拥有（`has_lyrics=1`）。
*   **降级提取内嵌兜底规范（退避保护）**：
    - 当偏好是 `network` 且网络刮削彻底失败（无搜索结果或接口均不可用）时，系统在结束任务前，必须执行**降级提取内嵌歌词的退避兜底保护**。
    - 若该歌曲的音频文件中含有原生内嵌歌词，则将其提取并保存至缓存，同时更新数据库标记 `has_lyrics=1`。此种退避成功不视为刮削失败，不累加 `scrape_retry_count` 重试计数。
*   **单曲检索控制与重试机制（防死循环请求与大循环开销）**：
    - 仅对满足 `scrape_retry_count < 3` 的歌曲发起刮削请求。
    - **无外层重复轮询**：每首歌曲仅单轮遍历平台提供商，废除外层 `3` 轮重复大重试机制，若一轮下来失败或核心数据保存失败，直接将该曲目的 `scrape_retry_count` 字段自增 1，直到上限 3 次。这能大幅缩减在遇到冷门歌曲时的无谓重试等待开销。新入库或物理文件大小/时间戳发生变动时重置为 0。
*   **线程与并发控制**：使用 `ThreadPoolExecutor` 限制最多 5 个并发 workers。
*   **串行延迟限流规范（精细化延迟）**：
    - 对单首歌曲，依次按 **QQ 音乐 -> 网易云 -> 酷狗** 接口顺序**串行**搜索，获取到有效封面/歌词并落盘成功后，标记数据库字段为 1 并提前退出。
    - **首个免休眠**：请求队列中的首个检索提供商时，直接发起请求，无需进行任何强制休眠。
    - **切换随机微休眠**：只有在切换到下一个提供商时，执行极短的频次安全防刷休眠，休眠时长区间设为极小的 `0.02` 至 `0.1` 秒（即 `time.sleep(random.uniform(0.02, 0.1))`）。
*   **实时聚合超时限制规范**：
    - 用户实时请求歌词或封面时，使用 `search_song_best` 并发请求。主线程等待所有平台检索子线程的最长超时时间为 `6.0 秒`（即 `t.join(timeout=6.0)`）。
    - 底层各平台 API 的所有 HTTP/HTTPS 网络请求，必须显式在客户端会话（如 `aiohttp` 或 `requests`）中硬编码不超过 `5.0 秒` 的单次请求超时限制。
*   **原子持久化一致性规范**：
    - 必须严格校验缓存落盘（如 `save_cover_file`）的写入成功返回值（必须非空）。只有在物理缓存文件确实写入成功后，才能把数据库中 `has_cover` 或 `has_lyrics` 更新标记为 1。
*   **打分与匹配阈值规范**：
    - 移除实时检索打分逻辑中的所有随机数微扰代码，保证搜索打分的幂等性与可预期性。
    - 针对“高质量结果优先”匹配策略（即有封面且歌词长度 > 50 字符），设置匹配文本打分卡口值 `0.55`。若得分低于该阈值，禁止强行降级匹配，防止发生异名同歌的“张冠李戴”错配。
*   **内嵌歌词提取类型限制规范**：为避免在处理 FLAC 等 Vorbis comment 结构时因检查非 ASCII 键名 `'©lyr'` 而触发 mutagen 内部 `ValueError` 异常，必须针对 `audio` 实例对象执行严格的 `MP4` 类型校验。仅当 `isinstance(audio, MP4)` 成立时，方可读取其 `©lyr` 标签属性。
*   **多平台检索缓存规范**：在底层各平台（网易云、QQ 音乐、酷狗音乐）的 `search` 入口统一使用 `@lru_cache(maxsize=64)` 进行缓存装饰。保证相同参数的连续检索（如先查封面、后查歌词）能直接命中缓存，降低对外网络请求频次，缩短实时刮削接口的整体延迟。
*   **物理包位置与重构规范**：废除顶层 `mod` 模块，将所有检索相关的核心算法与各大平台提供商接口转移并归入 `core.utils.search_network` 命名空间下。所有子模块通过包内相对导入进行交互，确保高内聚性和跨平台移植的自包含度。

## 2. 网易云异步下载管理器 (Downloader Service)

### 2.1 网易云本地容器接口桥接
*   **Cookie 注入机制**：调用本地 NCM API（`/song/url/v1` 等）时，自动拦截读取 `system_settings` 中的 `netease_cookie`，并作为 Header 和 params 透传，以保持 VIP 态。

### 2.2 异步下载任务状态机 (Download Task State Machine)
下载进程挂在单独后台线程中运行，各状态流转规范如下：
1.  **准备阶段 (`preparing`)**：
    - **状态转换卡口**：进入子线程后，**必须在执行任何封面抓取、元数据处理或网络请求前**，第一时间将任务状态更新为 `preparing`。这能避免网络拉取封面耗时导致状态长时间卡在 `pending`（排队中）状态。
    - 初始创建任务，向本地 API 接口补充获取歌曲的专辑信息、大图 picUrl。
2.  **地址抓取与音质回退机制**：
    - 请求 `/song/url/v1`。
    - **回退逻辑**：若指定的音质等级（如 `lossless`/`exhigh`）获取到的 URL 为空或属于无版权无收费，自动**回退到 `standard`（标准音质）**重新请求一次，确保最大化下载成功率，绝不因音质限制闪退。
3.  **下载中阶段 (`downloading`)**：
    - 流式下载文件 (`stream=True`)，每次块大小 8192 字节，并临时在物理路径追加 `.part` 后缀。
    - 实时通过下载大小比对计算百分比进度：`progress = int((downloaded / total_size) * 100)`，并以 WS 广播通知前端。
4.  **保存入库阶段**：
    - 物理移除 `.part` 后缀。
    - 对文件进行 MD5 哈希计算作为最终入库的 `song_id`。
    - 异步保存专辑大图到 `covers/` 目录并调用 `embed_cover_to_file` 内嵌到音频。
    - 异步拉取 `/lyric` 接口，保存 `.lrc` 与 `.yrc` (逐字) 歌词，并将 `.lrc` 内嵌到音频。
5.  **结束阶段 (`success` / `error`)**：
    - 自动清理超过 10 分钟的历史残留任务状态。
    - 物理调用 `index_single_file` 入库，并触发 `notify_library_changed`。
*   **下载任务池线程安全规范**：由于全局下载任务池 `DOWNLOAD_TASKS` 会被多个下载后台线程并发修改并由 Web 线程并发读取，必须使用线程锁 `download_tasks_lock` 强制保护对该任务池的增、删、改、查与活跃状态计数操作，防止高并发下产生字典读写冲突或字典迭代异常。

### 2.3 启动级残留临时文件物理清理机制 (clean_temp_part_files)
*   **清理时机**：主服务每次在 `__main__` 启动初始化时（在未开始执行网络端口与套接字监听前）同步拉起。
*   **清理范围**：
    - 自动遍历默认音乐曲库路径 `app_config.MUSIC_LIBRARY_PATH`。
    - 若配置了 `app_config.NETEASE_DOWNLOAD_DIR`，也一并遍历。
    - 遍历挂载点表 `mount_points` 下登记的所有目录。
*   **清理逻辑**：检测并物理删除所有以 `.part` 结尾的文件（这些是在线流式下载中途中断所留下的历史残留碎片文件），从而保证磁盘存储空间的整洁。
